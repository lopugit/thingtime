# PR 1357 — native scan pages and automatic attention

## Scope and cause

The previous 10,033-path mixed fixture spent 184.2 s across 316 native `scan-page` actions. Each page called Rust `status` and then `page`; the process transport launched a separate signed indexer process and opened SQLite for each call. Rust `page` already loaded status, checked snapshot/root identity and read the bounded ordered page transactionally. This PR returns that checked status with the page and validates it in `RustInventoryClient.checkedPage` and `MobileFolderInventory.read`. The Swift read still fences the saved record, bookmark, root identity, generation, capture, coverage, byte/page bounds and entry identities. It fails closed if the status is missing or disagrees. Other status callers remain unchanged.

The installed automatic-sync warning previously inferred changed settings solely from `job.state === 'attention'`. The journal had no reason field. This PR stores a fixed allowlisted reason and shows changed-settings guidance only for its typed configuration guard. Cloud 401/403 and 409/412 errors classify from the real stable transport format without storing raw response text. Older jobs and remote projections with no reason say that the cause is unavailable. Explicit Retry and Pause continue to own state transitions; no automatic resume was added.

## Matched native and end-to-end evidence

With the same source-built Rust indexer and 10,001-entry native capture, the 79-page read fell from **21,599 ms** before the fix to **11,353 ms** after it (47% lower). The changed read made exactly 79 `page` calls and zero separate `status` calls; exact paths/hashes and reopened-root checks passed. Rust's page test verifies the nested status agrees with page fields and still refuses a replaced root. A direct isolated process probe gave median 17.6 ms for capability-only startup and 24.4 ms for status with SQLite open/query across 25 runs. This is a lower bound, not a decomposition of the full 144 ms/page Swift measurement.

One isolated canonical Rust/native+HTTP fixture passed **1,032 paths and 26 files**: 1,000 imported sibling folders, six nested folders, 24 mixed files and two baseline files. It verified complete local/cloud checkpoints and exact hashes, accepted-reply loss, native/journal restart, unchanged zero transfer, and no duplicate publication. Setup/import was 79.9 s separately; first PUT was 39.7 s and unchanged run 31.5 s. Native `scan-page` totaled 15.95 s across 36 calls, while `scan-capture` totaled 24.56 s across four. These are diagnostic, with no same-input full-pipeline baseline. This wide fixture uses the complete paged fallback and has no early change feeds, so its first PUT follows capture/plan.

The dedicated two-way feed fixture proved early upload and download in the **same running, scanning, indexed-zero native generation**, exact bytes, one cloud revision, same capture after restart and no duplicate. With its deliberate 400,000 B/s scan ceiling, the first local event was 3.37 s, first admitted operation 11.65 s and first PUT 42.24 s. At the isolated normal 5,000,000 B/s scan/transfer and 15% CPU policy (effective Rust scan reservation 2,500,000 B/s), the final bounded fixture passed with a 512 MiB *sparse* late scan file: first local event 3.09 s, admitted `local.bin` 11.54 s and first PUT 42.10 s. The local payload was 65,537 bytes. First native inspect began 7.78 s, native read 20.03 s, upload create 25.10 s, native read-range 28.22 s, upload part 35.51 s and PUT 42.10 s. Cloud file publication began 59.91 s, native staging 69.48 s and native publication 79.69 s. The late file is only a disposable way to hold a real capture open; no physical-drive or production throughput claim follows from it.

Two normal-budget calibration attempts with a 128 MiB late file hit the unchanged 90 s proof deadline before the second receipt. Their bounded diagnostics were retained; one native inspect took 58.3 s, but the trace did not name the inspected path, so this is not assigned to the blocker as a proven cause. The 512 MiB sparse late file kept hashing beyond the before-seal proof and passed without changing that deadline or weakening receipt assertions. No more fixture reruns were made. The ~30.6 s admission-to-PUT gap under normal synthetic limits remains unassigned and needs a separate focused critical-path investigation. Cloud change-feed `GET /api/v1/files` calls include intentional long polls and their aggregate time cannot be summed as serial delay.

## Checks and limits

Focused Rust/Swift page tests, 27 journal/reason tests, Remix typecheck and changed-file lint passed. Isolated local and remote desktop/mobile attention screens passed full scroll and overflow checks under the test-owned browser. The structural Graphify snapshot and portable HTML/report were refreshed; Markdown semantic extraction was unavailable in this bounded pass. Process memory from the mixed run was integration-process-only RSS 468,288 KiB, not native/host memory or leak proof.

The fixtures use disposable account, database, index and local object store. They did not read personal folders, grant/resume Home, alter automatic policies or replace the installed app. Signed installed app delivery and the user's real attention-state recovery are separate final gates. The prior installed before-seal two-way proof and exact empty-file download remain valid for the unchanged product path; this PR's changed native indexer must still be rebuilt and accepted from the signed installed copy.
